2026-10-19 Linux culture encyclopedia: native static evidence
===========================================================

Scope and method
----------------
Inspected only the ELF, its existing disassembly and source text assets.
No game/process/product was started, attached to or injected. No input was
simulated. No tests, test cases, assertions or compilation were performed
for this evidence task. Addresses below are Linux ELF RVAs, not Windows RVAs.

ELF: /home/lulika/.local/share/Steam/steamapps/common/UnRealWorld/urw3-bin
Primary disassembly: build/analysis/linux-x86_64.asm
Focused extracts: build/analysis/culture-infobrowser.asm,
                  build/analysis/culture-links.asm
Text: game root GAME.NFO (CP437 bytes, CRLF), and
      gameinfo/urw_scrinfo.txt [.ENCYCLOPEDIA.] for the browser help panel.

The native encyclopedia owns topic lookup, history, document flow, pictures,
link detection, link hit boxes, selection, input, background save/restore and
presentation. Source-line identifiers are semantic asset identifiers; they
are not rows, line slots, coordinates or independently laid-out page records.

  514C8 -> 50CD0 link_show(char *sourceLine, char *topicHeader)
     RDI = current original body line; RSI = complete original dotted header.
     This is the complete semantic body-line translation boundary BEFORE
     native tokenization, text measurement, flow and link construction.
  514FB reads native picture filename after a '%' directive.
  5152F calls image with that original asset filename; 5154E reads next body.
  51495 closes file; 514A9 stores original current topic to topsnes 32F6E0.

F9680 fgetstr strips CR and LF and internally skips // and ## comment lines.
Therefore counting its CALLs does NOT give physical GAME.NFO line numbers.
Physical line keys require source-string/asset-offset mapping, or another
explicit source identity. A simple increment per fgetstr is incorrect.
The source record passed to link_show is distinct from eventual UI wrap rows.
Translation must not include original '%' picture directives or replace
English dotted topic lookup headers with Chinese.

Native tokenizer, flow and encoding boundaries
----------------------------------------------
50CD0 link_show(char *line,char *header)
  Original local source copies are 200 bytes; text accumulator is 1024 bytes.
  50D3C -> F9140 StrUpr on its matching copy.
  50D92 -> 1AFE00 SANATAULUKKO_Lisaa(1,sourceLine) makes native word slots.
  50D9F -> 1B00A0 resets native word-reading position.
  50DF0 -> 1B00E0 consumes word; 50E79 -> 1B00B0 peeks next word.
  50E1D and 50EB5 -> 13B460 textwidth BEFORE the native wrap comparisons.
  50EE5 -> 13E8B0 showtext, RDX = native current word.
  50F5E -> showtext of a literal ASCII space when the word lacks trailing
     space; 50F72 appends the same native space to its link matching buffer.
  50E3B / 50FA5 / 51023 / 51042 -> 50730 Lisaa_Linkit(...).
  50E40 / 51047 -> 50700 link_show_br, native cursor and line advance (+12).
  Native HYPER_X/HYPER_Y are 264600/2645FC; yie is 32F890.
  Their coordinates and wrapping decisions must not be copied into Mod tables.

1AFE00 SANATAULUKKO_Lisaa(int reset,char *source)
  Native word array SanaTaulukko=AA74B60, 130 bytes per word.
  Native entry index=AB13670. Splits only spaces and '<' / '>' markup.
  1AFE7D formats one byte; EBP advances source byte index.
  1AFF10..1AFF2D handles spaces; 1AFF78 '<', 1AFF38 '>'.
  Entire unspaced Chinese paragraphs therefore cannot simply be passed here:
  they would form one native word, neither wrap nor fit the word slot.
  A justified Chinese-token extension belongs at this tokenizer boundary;
  native words, peek/consume, wrap conditions and cursor remain native-owned.

F9140 StrUpr is NOT binary-safe for native Chinese two-byte tokens:
  F91F5 calls toupper per byte; F921B/F9228 explicitly remap bytes
  84/8E/E4 to C4 and 94/99/F6 to D6. Link-display copies at 50D3C/507A6
  require token-aware casing that preserves each encoded Chinese pair while
  retaining the game's original uppercase transformation for its legacy bytes.
  Internal English lookup paths (512B0/51383 etc.) are a different semantic
  boundary and must not be replaced by translated labels.

Native hyperlinks: identity separated from display
-------------------------------------------------
50730 Lisaa_Linkit(int x,int y,char *line,char *header,int measureOnly)
  RDI/RSI native text origin; RDX native mixed-text line; RCX original header;
  R8D selects original measurement-only/link-creation path.
  Native topics table=34E5C0, step 200; native current-page list=331100,
  history=32F980. Original English topic strings remain those structures'
  lookup, duplicate-detection, history and returned input values.
  507A6 -> StrUpr(line copy).
  50805 / 509B6 strstr match an original topic in the current line.
  508B6 strcmp checks already-present topic; 508E9 excludes current header.
  50963 / 50988 check original ASCII delimiter strings; '[' is special.
  Consequently an English topic token retained inside Chinese source needs
  native ASCII separation/markup. Chinese immediately touching its bytes is
  not accepted as the original delimiter by these checks.
  Original topic terms are matched case-insensitively. The scan is not limited
  to culture names: hunting, fishing, blacksmith and other GAME.NFO topics
  appearing in the culture descriptions also have original hyperlink meaning.

  Width call sites (all -> 13B460, RDI=complete string):
     509EE preceding text; 509FD topic; 50A19 preceding text; 50A28 topic;
     50A92 preceding text; 50B15 label; 50B7B label/underline extent.
  50A8A copies original English topic into native list using original length.
  50AB1 copies display label into native scratch, then normalizes '.' to space.
  50B43 -> F4E40 LIST_SpotEntry(int action,int x,int y,int width,int height)
     computes original mouse/selection hit box from the preceding text and
     label widths. This must consume the SAME Chinese display measurement.
  50BAC -> 143DA0 line draws native link underline using the same extent.
  50C39 -> 13E8B0 showtext, RDX=matched original display substring.
  50C71 stores original topic key in list and 50C76 advances lpos.

Confirmed implementation design available to the main task:
  Translate body source at 514C8 while retaining actual original linked-topic
  tokens. Convert those tokens to Chinese only for the above width/showtext
  calls, using identical conversion in both paths. Keep all native key storage
  and byte indices unchanged. For multiword labels, the selected display
  segmentation must be identical when measuring a whole prefix and drawing
  its individual words. Native spaces stay native spaces unless the explicit
  tokenizer extension proves and handles the corresponding boundary.
  This is display text conversion at confirmed native calls; it is not a
  second layout, pixel contribution log, overlay or delayed text replay.

Language redraw boundary and restrictions
-----------------------------------------
Existing adapter scopes cover culture selection separately from encyclopedia
topic input. The encyclopedia must have its own active native scope; treating
its LIST_Go as the outer culture selection would redraw the wrong native list.
topsnes at 32F6E0 identifies the native current topic. show_topic(topsnes)
rebuilds the topic and links, but also calls add_link and does not draw footer
buttons/help by itself. Repeating it unconditionally would change history.

One statically justified native rebuild sequence is cruise(current native
topic), with the redraw-only add_link call at 513CD suppressed. At the redraw
call at 5180D, invoke native link_select to build its navigation buttons but
return at its 5162C wait boundary through the native 5167B epilogue. The outer
5180D hook then resumes directly at cruise's native 51878 success epilogue,
without consuming the returned action. This is a native draw-only invocation;
it must not inject a QUIT/input action, execute real input, alter the saved
topic key or advance history.

The top encyclopedia header is drawn by infobrowser's 51B16, outside cruise.
Redrawing cruise alone does not update that header. To redraw it immediately,
the main implementation must reuse the confirmed original header-building
fragment, rather than copy the native title coordinates into a new Mod UI.
Current selection/cache restoration must follow F8630's native path after a
rebuild; the Mod must not retain pixel/text/position contributions for replay.

Implementation decision after static review: this delivery does not invoke
the redraw sequence described above. culture_browser keeps the language
selected at browser entry for the whole native encyclopedia session, restores
the outer scope/active_view on exit, and lets the next native browser entry
consume any newly selected global language. Immediate in-place language
refresh of the heading/body/help/list-cache combination remains unconfirmed;
no native history or input loop is replayed to simulate that capability.

Confirmed modern legend density chain and native rebuild boundary
  10AC3B's temporary surface is now a registered logical native target.
  Its original CreateSoftwareRenderer receives that expanded surface and
  the recorded actual output scale. rentextput -> renderer_text rasterizes
  each Chinese glyph synchronously at that renderer scale; it does not
  record text positions for deferred reconstruction or replay.
  10AE7F produces a registered CultureDialogTexture with the same density.

  Expanding the legend alone is insufficient: TextureToTexture(1428B0)
  copies it at 10B213 into MapviewMainTex. CompileMapviewSubscreen(10B0B0)
  owns this final UI target, destroys the old instance at 10B0C1, and calls
  CreateGamesizeTex at 10B0C6. That helper at 13C3B0 sets the original
  format/access and logical 800x600 size, then TAIL-JUMPS at 13C3D0 to
  SDL_CreateTexture. It has no inner CALL return site at 13C3EB.
  The owner stores the result at 10B0CB into global 665F680. Its background,
  help and controls are built by the original UI and retain logical units.

  The sole direct caller of CompileMapviewSubscreen is MapView's 10C8A6,
  immediately after 10C8A1 selects SDL_SetRenderTarget(NULL). The hook at
  10B0C6 therefore observes the native window renderer, after retirement of
  the previous MapviewMainTex and before any new legend copy is borrowed.
  It samples the actual window output density into separate mapview metadata,
  invokes native compile_CultureDialogTexture to rebuild its complete pixels
  using the current language/density, then invokes native CreateGamesizeTex.
  That creation scope registers the new MapviewMainTex at the same density.
  Native old/new legend ownership, surface release and renderer destruction
  remain inside compile_CultureDialogTexture itself. No independent layout
  or drawing history is retained. The ordinary screen canvas is not changed
  by this map-specific density sample.

  initgr's 148E07 is the only original direct legend-builder caller.
  CreateMapMainTexture(13A040) only rebuilds MapMainTexture and
  MapMainFinalTexture (native map-image textures); it does not rebuild this
  legend. Thus merely calling that resize function or updating screen canvas
  density would leave a previously compiled legend at its old density.
  Re-entering the complete native legend builder during MapView's confirmed
  target reconstruction supplies current-language glyphs at current density.
  This refresh occurs at native MapView reconstruction, not as an invented
  immediate language/input-loop refresh.

  TextureToTexture selects its original target at 1428ED, queries source
  dimensions at 142951 if native width/height are zero, and renders at 142909.
  Registered QueryTexture returns logical dimensions so native placement
  remains unchanged; the source still owns its full-density texture pixels.
  The new SetRenderTarget adapter applies the registered target's density
  after the original target selection. Original clipping/viewport resets
  and target lifetime remain SDL-owned.

  SDL2-compat release-2.32.72 src/sdl2_compat.c 5780..5805 confirms that
  SDL_SetRenderTarget first calls SDL3_SetRenderTarget, then resets a non-null
  target's viewport/clip, scale to (1,1), and logical presentation. Therefore
  density must be reapplied on each selection of a registered target.
  SDL3 release-3.4.16 src/render/SDL_render.c 2565..2598 confirms selecting
  NULL switches back to renderer->main_view, preserving the window view.
  The adapter does not rewrite the window scale with RenderGetScale's
  combined logical-presentation value.
  https://github.com/libsdl-org/sdl2-compat/blob/release-2.32.72/src/sdl2_compat.c#L5780
  https://github.com/libsdl-org/SDL/blob/release-3.4.16/src/render/SDL_render.c#L2565

  MapView chooses MapviewMainTex for SetFlipperMode at 10C8C7/10CBF5.
  MasterRender(146390) restores the window target if needed at 1463B2 and
  renders that whole texture at 1463ED with source/destination NULL, then
  Flipper presents through the native flow. This is the full-density final
  UI target; no low-resolution intermediate consumes the Chinese legend.
  MapView loads the final target at 10CE69, destroys it at 10CE70, and clears its native owner

Post-implementation static ABI review
-------------------------------------
Reviewed src/linux/culture_info.inc and its adapter/catalog/semantic wiring
without compiling or running them. The reviewed native interfaces match:
  * culture_preview_scope at 1C03C receives RDI=RBP (the culture key constructed
    in choose_culture's original local buffer), RSI=empty and EDX=0.
  * 4FEFE and 4FFFB are complete showtext calls with display text in RDX.
  * Browser wrappers at 106005/106DAD/106EFD receive their original topic in
    RDI and synchronously call infobrowser while isolating the outer scope
    and active_view. Their caller-owned save/restore paths remain outside.
  * At 51467/514FB/5154E, RDX is the original FILE*. ftell before the body
    reader gives the original CRLF record offset. Picture filename reads
    are followed by 5154E updating the next body-record offset.
  * 513F5 uses winbox's seventh original stack argument; 51B16 and 51910
    are five-argument TekstiPalkki calls with text in RCX.
  * All four navigation call sites use LIST_ButtonSpotEntry with text RCX;
    the dynamic original target at 330F60 is link[28] (32F980 + 28 * 200).
  * The language-spelling source boundary restores original CP437 byte 84
    for a taught lowercase ä character before the native tokenizer.
    Native StrUpr maps that byte to C4 for topic matching. Chinese token pairs
    remain intact at the two scoped uppercase calls, and the original word
    forms remain literal at both native measurement and drawing boundaries.
No blocking native ABI/lifecycle mismatch was found in those reviewed sites.
This is a static conclusion about the inspected boundaries, not a claim of
runtime results, completed target-density coverage or an executed test.
